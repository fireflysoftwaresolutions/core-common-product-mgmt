# Deposit document owner transport

The deposit publication coordinator requires current issuer and template/layout references. Its optional SDK resolver uses the original generated Configuration and Masters clients, constructing new authenticated clients for each owner call. The existing core binder checks the exact product/document tuple and retains the owner windows; it does not create publication authority.

Both `product.definitions.deposit.enabled` and `product.definitions.deposit.document-references.enabled` must be true to construct the resolver. The document-reference configuration requires `configuration-base`, `masters-base`, `configuration-issuer` and `masters-issuer`. Bases must be trusted HTTPS origins without user information, paths, queries or fragments. The production connector uses normal TLS verification and disables redirects; outbound requests and redirect responses are also checked before credentials can reach another origin. No endpoint, issuer, token or feature is enabled by default.

A genuine `ProductDocumentOwnerTokenProvider` bean is mandatory. Its implementation must verify the actual caller/delegation, allowed token issuer, owner audience, resource-tenant authority and exact requested product/document intent. Returned token data is an assertion from that trusted integration boundary, not authentication performed by a Java record. There is no default implementation, static token, incoming-header forwarding or audience fallback. Missing, empty, mismatched or expired delegation refuses before the owner request. Ambiguous or missing required application beans are configuration failures.

The original caller budget object passes through credential authorization and both owner SDK calls. One five-second wall/monotonic cap begins before credential I/O, and each earlier inherited, delegation and owner boundary remains binding. Credentials, SDK clients and bearer headers are isolated per invocation. The Masters effective-only observation preserves its null native deadline; no additional native stamp is inferred.

This is construction and controlled SDK transport wiring only. A configured sandbox identity/delegation integration and genuine signed owner HTTP qualification remain required. The same-version SDK coordinates still require exact source/artifact qualification and coordinated release adoption. The staged V25 activation fence remains false. Native schema/provider admission, rollback/recovery, raw-session/savepoint resistance, physical commit finality and financial publication are separate open gates.
