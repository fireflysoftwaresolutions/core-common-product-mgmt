# Current debit-card configuration

The opt-in `observeCurrentDebitCardDefinition` operation reads one exact tenant, Product root, Product, revision, and publication. It requires current `product.definition.debit-card.read` policy permission with `CARD_ENROLLMENT`, `BANKING`, and `DEBIT_CARD_V1`, plus the signed caller scope `product:definitions:debit-cards:read`. The original caller, audience, configured service client, expiry, and current policy are checked before and after the read. An opaque identity namespace requires the explicitly configured current Config tenant binding; it is never interpreted as a resource-tenant UUID.

The response carries the public debit definition, its exact publication graph and digest, the owner's canonical configuration, and finite observation times. It does not establish applicant KYC, an ownership mandate, account admission, issuer execution, shipment, activation, or card issuance. Those decisions belong to their respective owners. A public Product declaration that KYC or a mandate is required is not evidence that an applicant passed either check.

The service completes a protected mapped Spring Data read, obtains current Config document-issuer and Masters document-template/layout and currency observations through their complete generated SDKs, and then completes a second protected mapped read. Remote calls never run inside the SQL transaction. Both observations retain the original five-second budget and exact owner authority. A changed graph, withdrawn reference, changed caller, refused policy, empty owner result, or exhausted budget withholds the configuration. The operation never writes business data or supplies a new action/proof to another owner.

## Deployment

`product.definitions.debit-card-read.enabled` defaults to false. Enabling it requires the existing command configuration and receiver trust, a dedicated restricted reader login, explicit audience and client/tenant claim settings, and a genuine `DebitCardPurposeReferenceResolver`. The reference adapter is separately enabled with `product.definitions.debit-card-read.references.enabled`; it needs HTTPS Config/Masters origins, server-owned OAuth client-credentials registration IDs, and exact currency-policy routing selectors. Static selectors do not grant current owner permission.

The complete Config and Masters producers must expose `CARD_ENROLLMENT` in their existing document-purpose contracts. An older SDK that lacks this value cannot silently use `DEPOSIT_ACCOUNT_ENROLLMENT` or `INSURANCE_TERM_PC_QUOTE`. The current owner response must match every tenant, Product publication, document role, template/layout ID, opaque version, digest, document type, locale, and technical validity bound.

Before the additive V27 migration, an administrator must prepare the dedicated role/login using [the bounded reader template](../ops/database/debit-card-purpose/bootstrap-debit-card-reader.sql.template) and the existing [publication metadata ownership procedure](publication-metadata-deployment.md). Passwords come from the environment. Run V27 as the existing restricted publication installer; do not grant the application installer privileges or run the administrator template during application startup. The reader can access only the explicitly protected metadata columns. Private costs, commands, audit, history, and mutation privileges are not part of this capability. A drifted role or broadened grant fails closed.

For namespace binding, enable `product.definitions.debit-card-read.current-tenant-binding-enabled` and supply its HTTPS endpoint, machine registration, expected issuer, and opaque platform tenant. Missing or revoked current bindings do not fall back to direct UUID interpretation. Without this option, the existing strict signed UUID tenant contract applies.

## Qualification boundary

Source tests cover closed contracts, exact current authority, configuration defaults, current owner SDK transport, generated DTO/Instant behavior, and restricted mapped reads. The native read case compares all existing business rows and rejects foreign scope and widened reader privileges. These component and controlled-transport tests do not establish a signed multi-service Main journey. Deployment readiness also requires fresh complete controller-produced OpenAPI and SDKs, actual signed Main calls to all three owners, and retained no-effect observations. Generated canonical and SDK outputs are qualification artifacts, not committed replacements for tracked producer inputs.
